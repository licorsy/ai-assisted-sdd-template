Every Markdown documentation file in this repository, and every Markdown artifact the roadmap (`docs/strategy/roadmap.md`) generates while it executes, carries a YAML frontmatter block so the corpus can be filtered, embedded, and retrieved reliably — by a human searching the repo, or by a semantic-search/RAG pipeline indexing it. This document defines that schema and the rule for applying it.

## 1. Scope

Applies to:

- `agents/` — live subagent operating instructions: `orchestrator.md`, `phase-reviewer.md`, `tool-discovery.md`, `adversarial.md`, `init.md`, `doc-consistency.md`.
- `docs/manuals/` — the operation manual, this standard, the role guide, the prompt-engineering and agent-design guides, and the tool catalog; `docs/manuals/examples/` holds the worked examples an adopter replaces (governance, risk register, example ADR, and an optional Phase 1 PRFAQ scaffold).
- `docs/strategy/` — the execution roadmap and the optional go-to-market roadmap.
- `docs/adr/` — this template's real ADRs (`0002`-`0004`).
- `docs/visuals/` — the template visual overview.
- `docs/references/` — this template's own reference material for adopters: token-economy decisions, the unvetted tools-ecosystem shortlist, and the `infra-templates/`, `telemetry-template/`, and `gate-verification-template/` READMEs (nested one level deep; the lint walks recursively).
- `docs/prompts/` — historical/archived prompts and the blank prompt template, kept flat (see Section 4.1), plus `PROMPT-INDEX.md`, the id/status/purpose index over them (`doc_type: status-artifact`, Section 4).
- `docs/reports/` — external improvement reports and `PROPOSAL-TRACKING.md`, the status index tracking every proposal each report contains.
- Any Markdown artifact the roadmap generates elsewhere under `docs/` (e.g. `docs/business/`) or under `.specify/` during Phases 0-8 (see Section 7) — this is a *different* project's own generated content, coexisting under the same `docs/` root as this template's own `manuals/`/`prompts/` once the roadmap actually runs; see the reorg's own note in `docs/manuals/operation-manual.md`'s "Important note for this repository."
- `docs/STATE.md` — the generated repository-state facade (regenerated by `.github/scripts/generate-state.js`; hand-edits are a violation, see `docs/adr/0003-document-architecture.md` principle 3). It sits at the `docs/` root rather than in a category directory, so `.github/scripts/doc-scope.js`'s `CATEGORY_DIRS` does not reach it and the frontmatter-lint CI check does not cover it; its schema is maintained by the generator script instead.
- `docs/handbook.md`, `docs/status.md`, once they exist.
- `QUICKSTART.md` — the one root file in scope; it carries the schema (plus `diataxis: tutorial`) because it is indexed as a living tutorial doc.

Does **not** apply to:

- `.claude/agents/*.md` and `.claude/commands/*.md` — these already use Claude Code's own frontmatter contract (`name`/`description`/`tools`/`model` or `description`/`argument-hint`).
- `README.md`, `CLAUDE.md`, `AGENTS.md`, `CONTRIBUTING.md`, `SECURITY.md`, `CODE_OF_CONDUCT.md`, and `CHANGELOG.md` — the repository's entry points, not documentation-standard content. `CHANGELOG.md` follows the [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) format instead of this schema.
- Source code and tests. Extending structured metadata to source files (for example, Python) is a good idea in principle, but the idiomatic mechanism is different — structured module docstrings and `pyproject.toml`, not YAML frontmatter — and is out of scope for this document. Treat it as a separate future task.
- `local-notes/` — personal/instance-specific notes explicitly excluded from what this template presents; not documentation-standard content.

## 2. Required fields

Every file in scope carries all 8:

| Field | Type | Purpose |
| --- | --- | --- |
| `title` | string | Human-readable title, mirrors the file's H1; primary display string in search results and citations. |
| `doc_type` | enum | See Section 4. Drives faceted filtering. |
| `description` | string (1-3 sentences) | Doubles as the Dublin Core `description` and the embedding-friendly abstract for RAG; must stand alone without the body. |
| `status` | enum: `draft \| active \| deprecated \| archived` | Filters stale or superseded content out of default retrieval. |
| `version` | string (quoted) | Document revision, matches the file's own changelog convention. |
| `created` | date `YYYY-MM-DD` | Dublin Core `date.created`. |
| `updated` | date `YYYY-MM-DD` | Dublin Core `date.modified`; freshness signal. |
| `language` | string (ISO 639-1) | Dublin Core `language`, e.g. `en`. |

### 2.1 Body-changelog retention

Instruction, manual, and tool-catalog documents (`agents/`, `docs/manuals/`, `docs/strategy/`, `docs/visuals/`) keep a "Changelog of this document" list in the body, below the frontmatter. ADRs record revision history in their own `## Status`/`## Consequences` prose instead; worked examples under `docs/manuals/examples/`, `docs/references/` templates, `QUICKSTART.md`, and the generated `docs/STATE.md` carry none — the frontmatter `version`/`updated` pair plus `git log --follow` is the record for those. That list is a freshness aid, not an archive: keep only the **newest 3 entries** inline. When adding a new entry pushes the count past 3, remove the oldest in the same edit and keep a fixed closing line as the last list item: "Older entries: see `git log --follow` on this file." Git history preserves every removed entry verbatim; the frontmatter `version` field stays monotonic and is never reset by trimming. Never reword entries that stay; retention is removal-only. The cap is CI-enforced: the `changelog-retention` rule of `.docgov.config.js` (`licorsy/docs-governance`) fails any living document whose changelog list exceeds 3 version entries (prompt-055; moved from the repo-local `check-changelog-retention.js` script to the shared engine, see Section 9).

## 3. Optional fields

Add when meaningful:

| Field | Type | Purpose |
| --- | --- | --- |
| `id` | kebab-case string | Stable identifier decoupled from filename or version; the target of `related` links, so links survive renames and version bumps. |
| `tags` | array of strings | Free-form keywords for hybrid keyword+vector search and faceted filtering. |
| `owner` | string | Who to ask about the doc (Dublin Core `creator`/`contributor`). |
| `related` | array of `id` values | Graph-style retrieval expansion (Dublin Core `relation`) — for example, pulling in the roadmap when the orchestrator prompt is retrieved. Edges are directional, not required to be symmetric: list a document here when retrieving *this* file should pull it in; do not add a back-edge purely because another file points here. Hub documents (`roadmap.md`, `operation-manual.md`) are deliberately pointed *at* by many files without listing them all back. |
| `diataxis` | enum: `tutorial \| how-to \| reference \| explanation` | Only meaningful for `doc_type: product-doc`. See Section 5. |
| `phase` | string, e.g. `"Phase 1 - Discovery"` | Which roadmap phase produced or owns the artifact. Omit for docs not tied to a single phase. |
| `lastreviewed` | date `YYYY-MM-DD` | Only meaningful for `doc_type: tool-catalog`. File-level: the most recent date any entry in the catalog was added, edited, or reconfirmed accurate — not a per-entry claim (each entry's own "checked on" vetting-evidence field, see `tool-library-catalog.md`'s Entry schema, carries entry-specific freshness). Distinct from `updated`, which only means the file's content changed. |

## 4. `doc_type` values

| `doc_type` | Directory / artifact | Notes |
| --- | --- | --- |
| `instruction` | `agents/` (a live subagent's primary operating instructions), `docs/manuals/` (the operation manual, this standard), or `docs/strategy/` (the execution and go-to-market roadmaps) | Spans multiple physical folders; folder location is an orthogonal facet — whether a subagent reads the file directly as its own canonical operating instructions (`agents/`) versus broader human/orchestrator-facing operating-model guidance (`docs/manuals/`/`docs/strategy/`) — not a subtype of `doc_type`. |
| `manual` | `docs/manuals/`, `docs/visuals/` | Human-facing guides that are neither operating instructions nor a catalog: the role guide, the prompt-engineering and agent-design guides, and the visual overview. |
| `prompt` | `docs/prompts/` | Historical/archived prompts kept as flat reference material. No physical lifecycle subfolder; `status` alone conveys lifecycle stage. See Section 4.1. |
| `template` | `docs/prompts/`; the worked-example PRFAQ scaffold stays at `docs/manuals/examples/` | Same physical location as `prompt` in `docs/prompts/`; `doc_type` distinguishes a reusable blank scaffold from a prompt with real content. |
| `tool-catalog` | `docs/manuals/` | Single lean file (`tool-library-catalog.md`), not one file per tool; entry schema is defined inside the file itself. |
| `governance` | `docs/manuals/examples/` (this template's own worked examples); `/docs/` root in a generated project (`governance.md`, `risks.md`, scaffolded by `agents/init.md`) | Decision rights, risk register. |
| `adr` | `docs/adr/*.md` (real ADRs); the worked-example ADR stays at `docs/manuals/examples/` | Frontmatter `status` mirrors the ADR body's own `## Status` section: Accepted -> `active`, Proposed -> `draft`, Deprecated/Superseded -> `deprecated`. Keep the two in sync. |
| `status-artifact` | `docs/handbook.md`, `docs/status.md`, `docs/STATE.md`, `docs/prompts/PROMPT-INDEX.md`, `docs/reports/PROPOSAL-TRACKING.md` (`CHANGELOG.md` is out of scope — see Section 1) | Frequently-updated living-memory docs. |
| `product-doc` | `docs/*.md`, `docs/references/**/*.md`, `docs/reports/*.md` (external improvement reports; `PROPOSAL-TRACKING.md` is `status-artifact` instead — see the row above), `docs/business/*.md` (future), plus `QUICKSTART.md` (see Section 1) | Diataxis-governed per ADR-0001; use `diataxis` to refine. |
| `spec-kit-artifact` | `.specify/**/*.md` (future) | Spec Kit's own regenerable memory. Frontmatter here is best-effort: Spec Kit tooling may regenerate these files and could strip custom frontmatter. Do not treat this class as a hard guarantee. |

### 4.1 Prompt lifecycle state (no physical folder)

`doc_type: prompt` and `doc_type: template` files live together, flat, in `docs/prompts/`, regardless of lifecycle stage. There is no physical folder-per-status mapping: the frontmatter `status` field alone (`draft | active | archived | deprecated`) conveys lifecycle state. Moving a prompt between lifecycle stages means updating `status` in its frontmatter only — no file move is required.

Historical note: versions of this standard through v1.1 mandated a `draft/active/archived/deprecated` subfolder under `asset/prompt-library/` that mirrored `status`, with a folder/status mismatch treated as a standard violation. That structure was removed in the repo-wide reorg that produced `agents/` and `docs/manuals/` + `docs/prompts/`.

## 5. The `diataxis` field and ADR-0001

`docs/manuals/examples/adr-0001-documentation-and-governance-model.md` (Accepted) commits `/docs` content to the Diataxis framework — tutorials, how-to guides, reference material, explanation — for RAG-friendly search. This standard does not compete with that decision: `doc_type: product-doc` identifies which files fall under `/docs`, and the optional `diataxis` field classifies which of the four Diataxis categories a given file belongs to. Files outside `/docs` (instructions, manuals, prompts, governance, ADRs, status artifacts) are not Diataxis-classified; `doc_type` alone is sufficient for them - the one exception is `QUICKSTART.md`, indexed as a `tutorial`.

## 6. Transformation rule for legacy pseudo-metadata

Existing docs carry an informal bullet-list block under the H1 instead of YAML frontmatter. When retrofitting a file that has one, map fields as follows:

| Old field | New field | Rule |
| --- | --- | --- |
| `Purpose` | `description` | Copy verbatim. |
| `Language: English` | `language: en` | Convert to ISO 639-1. |
| `Version` | `version` | Copy verbatim, quoted. |
| `Created at` | `created` | Copy verbatim. |
| `Updated at` | `updated` | Copy verbatim. |
| `category` | `doc_type` | Lowercase (`Prompt` -> `prompt`, `Manual` -> `manual`). |
| `index` | *(dropped)* | Redundant with the filename or `id`. |
| `Author` / `Executed by` | `owner` | Deduplicate; do not carry both. |
| `Executed at` | *(dropped)* | Redundant with `created` in every case observed so far. |

Files with no prior pseudo-metadata at all get `created`/`updated` from `git log` evidence (first-added date, last-modified date) rather than a guess. Never fabricate a date that isn't supported by either the file's own content or its Git history.

## 9. Verification checklist

Enforcement is prompt-based for the checks below; a GitHub Action (`.github/workflows/pr-checks.yml`'s `ci-docs` job, delegating to `licorsy/platform-workflows`'s reusable `ci-docs.yml`, which runs `licorsy/docs-governance`; originally `docs-frontmatter-lint.yml`, prompt-013, then the standalone `docs-governance.yml`, prompt-NNN — TBD) automates checks 1, 2, and 3 for every directory in `.github/scripts/doc-scope.js`'s `CATEGORY_DIRS`, plus `QUICKSTART.md` (Section 1's one in-scope root file), on every push and pull request; the same workflow's `internal-links` rule (originally `.github/scripts/check-internal-links.js`, prompt-017) automates check 4 for link-formatted references. What stays manual: check 2's `adr`-status-mirrors-body rule, check 4 for paths mentioned as inline code rather than as Markdown links, and check 5's `tool-catalog` freshness bump. Whoever creates or updates an in-scope file confirms:

1. **Structural** — the file starts with `---`, has a closing `---` before the H1, and all 8 required fields (Section 2) are present and non-empty.
2. **Enum** — `doc_type` matches the file's actual location (Section 4); `status` is one of the four allowed values; for `adr`-typed files, frontmatter `status` matches the body's own `## Status` section.
3. **Cross-reference** — every `related` entry resolves to another file's `id`.
4. **No dangling paths** — any file path mentioned in the frontmatter or body still exists in the repository.
5. **Tool-catalog freshness** — for `doc_type: tool-catalog` files, `lastreviewed` (file-level) is bumped to today whenever any cataloged entry is added, edited, or reconfirmed, even without a content edit to that entry's prose — it tracks the catalog's most recent review activity as a whole, not any single entry's freshness.
